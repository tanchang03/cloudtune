# CloudTune 云韵音乐 · 设计思路审计与风险评估

> 版本 v0.1（**进入开发前的评审材料**） · 2026-09-23
> 审计对象：`01-需求分析与产品设计.md` + `02-技术架构与接口设计.md`
> 审计目的：在写第一行业务代码之前，把「能不能做、风险在哪、哪条路不能走」说清楚

---

## 1. 审计结论摘要

**总体结论：产品方向成立，但必须修正三处前提，否则会在开发中途返工。**

| 你的需求 | 可行性判定 | 一句话说明 |
|---|---|---|
| ① 授权夸克账号 | ⚠️ **有条件可行** | 夸克有开放平台但**仍在内测、文档未公开**；且官方接口**没有"列目录"能力** |
| ② 遍历搜索全部音乐文件 | ⚠️ **有条件可行，且有覆盖盲区** | 阿里/百度可完整递归；**夸克只能靠搜索接口近似遍历，无法保证 100% 覆盖** |
| ③ 随机播放 + 喜欢收藏 | ✅ **完全可行** | 纯客户端逻辑，无外部依赖，是最稳的部分 |
| ④ 扩展到阿里云盘 / 百度网盘 | ✅ **可行** | 两家都有正式开放平台；但准入条件与限流差异大，需按序接入 |
| ⑤ Flutter 全平台兼容 | ⚠️ **需修正口径** | 移动端 + 桌面端可行；**Web 端因 CORS 与请求头限制，无法播放百度直链** |

**一句话**：核心风险不在"播放器"，而在"网盘接口"。
播放器本身是成熟技术（`just_audio` 生态完备），真正的未知数全在**夸克**。

## 2. 四处必须修正的前提

### 前提修正一：夸克不是"接个 API"这么简单

**事实**（已核实）：
- 夸克确有开放平台 `open.quark.cn`，但**尚在内测、未公开完整文档**。
- 目前流通的夸克接口资料，是**第三方对客户端打包产物的静态逆向分析整理**，非官方文档。
- 其鉴权是 `SHA256(METHOD&PATH&TM&SIGN_KEY)` 签名头 + OAuth 双重要求，还硬编码了默认客户端凭据。
- **官方接口清单里没有 `list_dir`（列目录）**，遍历只能靠 `POST /agent/v1/file/search` 分页搜索。

**这意味着什么**：
1. **授权环节**：如果拿不到内测资格，只能走逆向签名方案，而逆向方案的接口契约、限流规则、风控策略**全都不公开**，随时可能变更。
2. **遍历环节**：需求 ② 的"遍历所有音乐文件"，在夸克侧**在原理上就无法保证完备**。搜索接口需要关键词/分类驱动，你无法像 `list_dir` 那样确定性地枚举一个目录。
   - 后果：用户可能反馈"我明明有这首歌，播放器里搜不到"。
   - 这必须在 UI 上如实说明，不能承诺"已扫描全部文件"。

**建议的三条路线**：

| 路线 | 做法 | 优点 | 缺点 | 建议 |
|---|---|---|---|---|
| A. 官方内测 | 申请 `open.quark.cn` 接入 | 稳定、合规、可持续 | 需审核，文档未公开，周期不可控 | ✅ **主线** |
| B. 逆向接口 | 复刻签名算法 + OAuth 流程 | 立刻能跑 | 无契约保证、可能违反 ToS、随时失效 | ⚠️ 仅作 PoC 与兜底 |
| C. Cookie 导入 | 用户手动粘贴 Cookie | 最快 | 最脆弱、易触发风控、安全观感差 | ❌ 不作为主线 |

**架构应对（已体现在设计中）**：把夸克封装在 `CloudDriveAdapter` 之后，
`QuarkAuthStrategy` 做成可插拔（官方签名 / 逆向签名 / Cookie），
**上层业务代码完全不知道下面走的是哪条路**。这样路线切换的成本被压到最小。

### 前提修正二："全平台兼容"要改成"分级承诺"

**事实**（已核实）：

| 平台 | 播放 | 自定义请求头 | 后台播放 | 结论 |
|---|---|---|---|---|
| Android / iOS | ✅ | ✅ | ✅ | 全功能 |
| macOS / Windows | ✅ | ✅ | ⚠️ 仅托盘 | 全功能（后台略弱） |
| Linux | ✅ | ✅ | ⚠️ 较弱 | 基本可用 |
| **Web** | ⚠️ | ❌ **不支持** | ❌ | **不能播百度** |

两个硬约束：
1. **百度网盘直链必须携带 `User-Agent: pan.baidu.com`**，而浏览器 HTML5 Audio 无法设置自定义请求头 → **Web 端从原理上播不了百度**。
2. **CORS**：网盘直链域名不会为第三方 Web 站点开放跨域 → Web 端大概率连阿里云盘也播不了。

**建议口径**：
- 对外表述改为「**移动端 + 桌面端全平台**」，Web 端定位为**浏览与管理端**（看库、管理收藏、看统计），不承诺播放。
- 如果一定要 Web 能播，唯一的技术解是**自建代理中转** —— 但这直接踩中下一节的红线，**坚决不做**。

### 前提修正三：扫描速度会远低于预期，必须提前做预期管理

**事实**（已核实的阿里云盘限流）：

| 接口 | 普通应用配额 |
|---|---|
| `openFile/list`（列目录） | **10 秒 40 次** |
| `getDownloadUrl`（取直链） | **10 秒 10 次** |
| 其余 API | 15 QPS |
| 分段下载并发（单用户单应用） | **1 秒 3 个并发** |

**推算**：假设你有 800 个目录，仅列目录就需 800 ÷ 4 ≈ **200 秒**（受 40次/10秒 约束，实际约 200 秒是理论下限）。
再加夸克只能搜索式遍历（每次 `size ≤ 100` 且需翻页），
**1 万文件量级首次全量扫描，3～8 分钟是现实预期，不是悲观估计。**

**设计应对（已体现在设计中）**：
- 异步后台扫描 + 进度可视化 + 可暂停续扫（`scan_cursor` 表）
- 增量扫描：二次扫描只拉变化目录
- 本地索引库打开即用，**日常使用零网络请求**
- 用户可调并发数（默认保守）

### 前提修正四：夸克侧有 ~50 MB 单文件体积上限，过半曲目无法在线播放

> **📌 本节的结论已被证伪（2026-09-24），见 §6 下方的「后续更正」。**
> 那条 50 MB 上限只约束 `download` 这一条路由；播放主路由 `/file/audioplay`
> **不受体积限制**，抽样 40 首「超限」曲目全部可播。
> 本节保留原文，作为评审当时的记录。

**事实**（PoC 实测，2026-09-23）：

- 取直链接口 `/1/clouddrive/file/download` 对超过约 **50 MB** 的单文件返回
  `code=23018 download file size limit`。
- 边界实测：≤48.6 MB 成功，≥53.2 MB 失败。
- **账号为 `member_type: SUPER_VIP`（6 TB 容量）**，因此这不是免费用户的限制，
  而是该 API 路由本身的上限。
- 9 种参数（`fr=pc/pc_web/android/ios/mac`、无 `pr/fr`、加 `sys`）与 2 个替代端点全部无法绕过。
- 官方开放平台（`open-api-drive.quark.cn`）是否有同样限制**尚未验证** —— 那是内测接口，
  需要拿到资格后才能测。这是 M1 阶段要优先确认的问题。

**对当前音乐库的实际影响**：

| 指标 | 数值 |
|---|---|
| 可在线播放 | **239 / 444 首（53.8%）** |
| 可播体积占比 | **7.5 GB / 37.2 GB（20.2%）** |
| flac | 232 / 397 可播 |
| wav | 7 / 29 可播 |
| **dsf** | **0 / 18 可播（全部超限）** |

**这意味着什么**：

1. 「随机播放」不能对全库随机 —— 必须**只在可播集合内随机**，否则会频繁卡在播不出来的曲目上。
   这直接修改了需求 ③ 的实现方式。
2. 用户的高解析收藏（DSD / 整轨 WAV）**通过这条路基本听不了**。
   而这类用户恰恰最可能是「网盘囤歌党」——目标用户画像与能力边界存在错位，需要在产品定位上说清楚。
3. 这是**网盘侧的限制，不是产品缺陷**，UI 上必须如实说明，否则用户会认为是播放器坏了。

**设计应对**：

- 新增需求 C12（可播性预判与标记）、C13（超限降级策略），已写入 `docs/01` §3.3。
- 随机播放范围限定为「当前筛选范围 ∩ 可播集合」。
- 决策点 D9 待你拍板降级策略的深度。

## 3. 逐项设计审计

### 3.1 授权设计 —— 通过，但需补三点

✅ OAuth2.0 标准流程设计正确。
🔧 **需补充**：
1. **桌面端回调**：`redirect_uri` 用 loopback（`http://127.0.0.1:随机端口`）而非自定义 scheme，兼容性更好。
2. **Token 存储**：必须用系统钥匙串（`flutter_secure_storage`），**禁止**写进 SQLite 或日志。
3. **时钟偏移**：夸克签名依赖时间戳 `x-pan-tm`，本机时间不准会导致 `errno 10001 签名验证失败`。需在错误处理里加"检测系统时间偏移"的提示。

### 3.2 遍历设计 —— **本项目最大风险点**

✅ 抽象正确：`listDir` + `search` 双通道 + `Capabilities.supportsListDir` 能力声明。
⚠️ **风险**：夸克无 `list_dir`，只能"搜索式近似遍历"，**覆盖不完备**。
🔧 **需补充**：
1. UI 必须区分展示"**已确认扫描的目录**"与"**搜索发现的文件**"，不要给用户"已全盘扫描完成"的错觉。
2. 提供「**手动补充扫描**」入口：用户可指定目录或关键词做定向补扫。
3. 提供「**刷新单曲直链**」：即使索引里没有，用户手动粘贴文件链接也能播。

### 3.3 随机播放设计 —— 通过

✅ Fisher-Yates 洗牌队列 + 加权抽样，是成熟且正确的做法。
✅ 避免"裸随机"导致的长尾歌曲永不播放，考虑到位。
🔧 建议补充：提供「**随机种子/可复现**」选项（调试与用户"重听上次的随机列表"有用）。

### 3.4 收藏设计 —— 通过，但有一个语义要澄清

✅ 本地持久化 + 可选导出，方向正确。
⚠️ **需澄清**：收藏**是否要同步到网盘**？
- 若同步到网盘（例如在网盘建一个"我喜欢"文件夹或生成 m3u 文件），需要 `file:all:write` 权限，
  且会产生**写操作**，与"只读更安全"的设计原则冲突，也会让授权范围变大（用户更容易拒绝授权）。
- **建议**：MVP 阶段**收藏纯本地**，通过 JSON 导出/导入做换机迁移。后续再评估网盘侧同步。

### 3.5 播放设计 —— 通过

✅ "不缓存直链、播放时实时换取"的设计**完全正确**，这是被直链过期问题逼出来的唯一正解。
✅ 直链自愈（403 → 重取 → seek 续播）是必须的，设计里有。
🔧 **需补充**：`getDownloadUrl` 阿里云盘限 **10 秒 10 次**，快速连切歌可能触限。
→ 应加**直链预取队列**：只预取"下一首"，且与当前播放的取链请求共享同一个限流桶。

## 4. 被否定的方案（及否定理由）

审计的价值一半在于说"不能做什么"。

| ❌ 被否定的方案 | 否定理由 |
|---|---|
| **自建后端服务器中转播放** | ① 阿里云盘开放平台明确把「将播放链接挂到外网做播放网站」列为**风险应用降级/封禁条件**；② 中转即意味着你的服务器在转发用户文件流，法律与成本双重风险；③ 违反「纯客户端直连」原则。**坚决不做。** |
| **把逆向夸克接口作为唯一技术路线** | 无契约保证、可能违反服务条款、接口随时变更导致产品"一夜失效"。仅可作为兜底与 PoC。 |
| **全量下载到本地再播放** | ① 违背"不搬家"的产品初衷；② 网盘动辄几百 GB 音乐，本地存不下；③ 下载本身也受并发限制（1s/3 并发）。**降级为 P2 可选的单曲缓存。** |
| **Web 端承诺全功能播放** | 技术上做不到（CORS + 无法自定义请求头），承诺了就是给自己挖坑。 |
| **用网盘官方 App 图标或近似设计** | 阿里云盘开放平台明文列为降级条件：「使用阿里云盘 App 的图标作为应用图标，或冒充云盘官方诱导用户授权」。 |
| **收藏同步写回网盘** | 需要写权限，扩大授权范围降低授权通过率；MVP 收益低。 |

## 5. 合规红线自查清单

来自阿里云盘开放平台《应用分级》明文列出的**风险应用判定条件**，逐条对照本项目：

| 红线 | 本项目是否会踩 | 应对 |
|---|---|---|
| 存在分享开发者账号（appid/secret） | ❌ 不会 | client_secret 打包进客户端，**必须做代码混淆**，且不对外公开仓库 |
| 存在泄露或分享用户数据的风险（含 token、下载链接、播放地址） | ❌ 不会 | 纯本地存储，**零自建服务器**，不上报任何用户数据 |
| **存在使用非阿里云盘官方开放 API 的情况** | ⚠️ **需注意** | 阿里云盘适配器**只走官方 OpenAPI**，绝不混用逆向接口 |
| 存在显著安全漏洞 | ❌ 不会 | token 走钥匙串；不记录明文日志；传输强制 HTTPS |
| 使用云盘 App 图标冒充官方 | ❌ 不会 | 使用独立品牌视觉，授权页明确标注「第三方应用，非官方」 |
| 图床/软件床/视频站等文件分发服务 | ❌ 不会 | 产品定位是**个人播放客户端**，不提供任何对外分享能力 |
| 读取本机其他应用私有凭据（模式 D） | ⚠️ **仅 PoC 阶段** | 限定为本机自用验证；不进发布路径；凭据只驻留内存；设置页提供一键清除 |

**补充合规动作**：
1. 授权页显著位置声明：「本应用为第三方独立客户端，与各网盘官方无关联」。
2. 首次启动展示隐私说明：**所有数据仅存本地，不上传任何服务器**。
3. 不做任何形式的"加速下载""破解会员"功能。
4. 遵守各平台服务条款，不做高频轮询（用限流器 + 增量扫描约束）。

## 6. 风险登记册

| # | 风险 | 概率 | 影响 | 等级 | 应对措施 |
|---|---|---|---|---|---|
| R1 | 拿不到夸克开放平台内测资格 | **高** | 高 | 🔴 | 备选逆向方案已设计为可插拔；提前启动申请；先做阿里云盘验证产品价值 |
| R2 | 夸克逆向接口变更导致失效 | **高** | 中 | 🟠 | 适配器隔离；把夸克标记为"实验性接入"；失败时优雅降级而非崩溃 |
| R3 | 夸克遍历覆盖不全，用户找不到歌 | **高** | 中 | 🟠 | UI 如实说明 + 手动补扫入口 + 支持手动粘贴文件播放 |
| R4 | 触发网盘风控（限流/封禁） | 中 | **高** | 🟠 | 限流器 + 保守并发 + 指数退避 + 用户可调并发 |
| R5 | 阿里云盘应用被降级为"风险应用" | 低 | **高** | 🟠 | 严守合规清单；只读权限；绝不中转；绝不对外分享直链 |
| R6 | Web 端播放不可用引发用户投诉 | 中 | 低 | 🟡 | 明确分级承诺，Web 端定位为浏览管理端 |
| R7 | Flutter 桌面端音频后端（Windows/Linux）不稳定 | 中 | 中 | 🟡 | 优先做 macOS/Android 验证；桌面端列为第二梯队 |
| R8 | client_secret 被打包进客户端被提取 | **高** | 中 | 🟡 | 代码混淆 + 申请时如实说明是"公共客户端"；接受此风险（OAuth 公共客户端本就无法完全保密） |
| R9 | 网盘直链有地域/网络限制（如海外 IP 无法播） | 中 | 中 | 🟡 | 提供代理设置入口 |
| R10 | 项目范围过大，长期无法交付 | **高** | 中 | 🟠 | 严格按里程碑推进，M1 只做夸克，先跑通闭环 |
| R11 | 本机会话复用（模式 D）被误当作正式方案，导致移动端无法交付 | 中 | **高** | 🟠 | 代码中显式标 `experimental`；产品功能清单不写入；平台能力矩阵已标注「仅桌面端」 |
| R12 | 会话复用凭据泄露（Cookie 明文落盘 / 日志泄漏 / 崩溃上报） | 中 | **高** | 🟠 | 凭据只驻留内存，不落库不打日志；禁用该路径下的崩溃上报；设置页提供一键清除 |
| R13 | **夸克 50 MB 体积上限导致过半曲目无法在线播放**（实测 53.8% 可播、DSF 100% 超限） | **已发生** | **高** | 🔴 | 扫描期预判并标记「不可在线播放」；UI 明确提示；超限曲目引导本地缓存（P2）；向用户说明该限制来自网盘侧 |
| R14 | 直链必须带 Cookie，导致播放器实现受限 | **已发生** | 中 | 🟡 | 播放引擎统一走「带请求头的 AudioSource」；Web 端已排除 |

**最高优先级：R1、R2、R4、R10** —— 建议**开发第一件事就是做夸克的授权 + 扫描 PoC**，
用最小成本证伪，而不是先搭 UI。

> ### 📌 后续更正（2026-09-24）
>
> **R13 的结论已被证伪，不要按它做设计。** 上面那条「50 MB 上限导致过半曲目无法在线播放」
> 是**只看 `download` 一条路由**得出的结论。
>
> 后续发现 `/1/clouddrive/file/audioplay`（音频专用播放接口）**完全不受体积限制**：
> 实测 774.1MB 的整轨 WAV 同样返回 `code=0` + 原文件直链，库内 195 首「超限」曲目
> 按体积降序抽样 40 首**全部可播**。因此 `QuarkCapabilities` **刻意不声明**
> `maxSingleFileBytes` —— 写了会让约 43.9% 的曲目被误判为不可播。
>
> 那条 50 MB 限制仍然真实存在，但它只约束 `download` 这条**兜底**路由，
> 不再是「过半曲目无法播放」的产品级问题。
>
> 原始结论保留在上方，作为评审当时的记录。

### 7.1 关于 D8 的专项说明

你提出「调用本机夸克运行程序的 token」这条思路。**技术上成立**，已在本机实测确认：

> **📌 公开版本已脱敏（2026-09-24）**：原先记录的凭据落盘路径、表结构与解密做法已移除，
> 只保留结论。该通道**从未进入发布路径**，原因见下方四条硬限制。

- 夸克桌面端有三处凭据落盘（Electron 客户端 / 夸克浏览器 / 网盘客户端），均为标准 Chromium SQLite cookies 表。
- 其中旧 Electron 客户端那份是**明文存储**，读取无需系统授权。
- 夸克浏览器那份是加密的，读取会触发系统授权弹窗；但它是当前唯一新鲜的会话。

**但有四条硬限制，决定了它不能成为产品方案**：

1. **平台锁死** — 仅 macOS/Windows 可行。iOS 沙箱不可能，Android 需 root。**移动端永远用不了**，与「Flutter 全平台」直接冲突。
2. **本机锁死** — 凭据是本机产物，无法分发、无法跨设备同步，每个用户都得在自己电脑上单独准备。
3. **生命周期不可控** — 会话会过期、会静默轮换，客户端一刷新就失效，用户需反复重新获取。
4. **合规等级上升** — 已不属于「使用官方开放 API」，而是读取其他应用私有凭据。打包分发性质更重。

**结论**：作为**开发期 PoC 通道**是最优解（正好解决「没有内测资格如何验证」这个当下最痛的问题），
但**不进正式发布路径**。它的附带价值是反向验证 `CloudDriveAdapter` 抽象是否够用。

**另一个值得先确认的发现**：三处存储都出现了 `access-open.quark.cn` 的 cookie，
说明你的浏览器访问过夸克开放平台。如果已经注册过开发者应用、拿到 `client_id`，
走标准 OAuth 授权码流程会比会话复用干净得多 —— 建议先确认这一点，再决定 PoC 走哪条。

### 7.2 PoC 实测结果（2026-09-23）

你确认暂无 `client_id`，PoC 按模式 D 执行（研究期脚手架，不随本仓库公开）。结果如下：

| 验证项 | 结果 | 说明 |
|---|---|---|
| 本机凭据可否程序化读取 | ✅ 可以 | 明文库可完整取出会话令牌（**该通道未进入发布路径**） |
| 接口链路是否正确 | ✅ **已验证** | 用真实会话返回 `HTTP 200 / code=0` |
| 现有会话是否有效 | ✅ 有效 | 用户手动提供 Cookie 后全部接口正常 |
| 加密库能否解密 | ❌ 未破解 | 700 次穷举全落空，判定为**夸克自研加密** |
| **遍历（递归列目录）** | ✅ **可行** | 250 目录 / 2592 文件 / **444 首音乐 / 37.23 GB** |
| 搜索接口 | ✅ 可用 | `mp3`、`flac`、歌手名 各返回 50 项 |
| 取直链 | ✅ 成功 | `code=0`，返回 `download_url` |
| **Range 边下边播** | ✅ **可行** | 带 Cookie → `HTTP 206` + `Accept-Ranges`，首字节 `fLaC` |
| **单文件体积上限** | ⚠️ **~50 MB 硬限制** | ≤48.6MB 成功，≥53.2MB 报 `code=23018` |
| 绕过体积限制 | ❌ 未找到 | 9 种参数 / 端点变体全部无效 |

**两个关键信号，值得记录**：

1. **接口层已无未知数**。用假 Cookie 请求得到 `code=31001 require login [guest]`，
   用过期真令牌得到 `code=31004 token invalid` —— 服务端能区分「访客」与「令牌失效」，
   证明**域名、请求头、参数、Cookie 组装方式全部正确**。剩下的只是会话有效性问题。
2. **当前客户端只写加密库**。`quark-cloud-drive/`（明文）属旧版客户端 v3.24.0 的遗留，
   当前客户端 v6.5.0.709 二进制中不含该路径，说明升级后已改用 `QuarkCloudDrive/`，
   **明文库不会再被刷新**，指望它自动变新是不可行的。

**结论与影响**：

- 模式 D 的**接口部分已验证可行**，全链路（遍历 → 搜索 → 取直链 → Range 播放）全部跑通。
- 自动化获取会话受阻于自研加密，故改为**手动提供 Cookie** 通道（已实现并验证代码路径）。
- 这进一步**强化了「模式 D 只能做 PoC」的定位**：连获取会话都需要人工介入，
  不可能作为面向用户的产品功能。
- **正式路线不变**：申请 `open.quark.cn` 内测，走官方签名 + OAuth。

**PoC 额外发现的两条硬约束（已回写至需求与架构文档）**：

1. **直链必须携带 Cookie** —— 请求头矩阵 11 种组合实测：裸请求 / 仅 Referer / 仅 UA 全部
   `HTTP 412 Precondition Failed`，**任何带 Cookie 的组合**才返回 `206` + `fLaC`。
   `412` 而非 `403`，说明缺的是「前置条件」即 Cookie。
   → 播放器**必须支持自定义 HTTP 请求头**，浏览器 HTML5 Audio 做不到，
     **再次印证 D3（Web 端排除出 MVP）的正确性**。

2. **~50 MB 单文件体积硬上限** —— 账号实测为 `member_type: SUPER_VIP`（6 TB 容量），
   所以**不是会员等级限制**，而是该 API 路由本身的上限。9 种参数 / 端点变体均无法绕过。
   对当前音乐库的实际影响：

   | 指标 | 数值 |
   |---|---|
   | 可在线播放 | **239 / 444 首（53.8%）** |
   | 可播体积占比 | **7.5 GB / 37.2 GB（20.2%）** |
   | flac | 232 / 397 |
   | wav | 7 / 29 |
   | **dsf** | **0 / 18（全部超限）** |

   → 这是**产品级约束**，必须新增「可播性标记」与「超限降级策略」（见 `docs/01` §3.3 C12/C13）。

## 9. 审计结论

**可以做，但要按"先证伪、再放大"的顺序做。**

- 产品价值成立：多云盘统一音乐库 + 在线直连播放 + 随机 + 收藏，是个真实且没人做好的需求。
- 技术主干成熟：`just_audio` + `audio_service` + `Drift` + 适配器模式，都是经过验证的组合。
- **唯一的高不确定性集中在夸克**，而它恰好是你需求的起点。
- 因此强烈建议：**先花半天做夸克 PoC，再决定投入规模**。如果夸克这条路走不通，
  阿里云盘 + 百度网盘同样能支撑这个产品的核心价值，只是要重新和你确认产品定位。
